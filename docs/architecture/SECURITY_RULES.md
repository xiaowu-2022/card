# Security Rules

Tenant host resolution and membership scope are server-authoritative. Client-provided tenant identifiers are ignored. Authorization is enforced by backend policy/permission checks; hidden UI controls are only UX. Platform Admin is isolated on its own host and user/admin identity stores are separate.

End User authentication uses its own `tenant_user` guard. Login resolution begins with `tenant_id + normalized email/phone`; a Tenant-aware Eloquent provider also scopes session restoration by resolved `tenant_id + user_id`, and middleware clears missing, mismatched, or DISABLED identities before shared props/controllers run. Anonymous failures use generic credential/challenge errors. Successful login/registration regenerates the session. Guard-scoped logout rotates the session id while preserving a separate Admin guard session on the same Tenant host.

Registration OTPs are six cryptographically generated digits, stored only as HMAC-SHA256 over `challenge_id:code` with a server secret, checked with constant-time comparison, expired after configured TTL, and locked after configured attempts. Using `APP_KEY` as the default secret means APP_KEY rotation intentionally invalidates outstanding short-lived challenges. PostgreSQL challenge state is authoritative and verified completion also requires the initiating browser session; a UUID alone is insufficient. Rate limits cover Tenant+destination and Tenant+IP sends plus Tenant+identifier+IP login; normalized contacts are hashed before key construction. OTPs, code hashes, passwords, and full auth requests are excluded from audit/log context. Email uses Laravel Mail/Mailpit locally; unavailable SMS is not advertised and no SMS implementation may print an OTP to logs.

Platform and Tenant Admin use distinct session guards. A valid password alone is insufficient: AdminUser status, membership status, scope, resolved Tenant, role, and permission are checked on every protected route. Successful login regenerates the session identifier; logout invalidates it and regenerates the CSRF token without deleting identities, memberships, or invitation history. `SESSION_DOMAIN` must remain unset/empty, the cookie path is `/`, HttpOnly is enabled, and Secure cookies are required in production. Host-only cookies prevent a Platform or Tenant login cookie from becoming a parent-domain credential. Both login surfaces use email/IP/surface rate limiting and fixed internal redirects. Production deployments must trust only explicitly enumerated reverse proxies and sanitized forwarded headers; wildcard proxy trust is forbidden.

`SensitiveDataRedactor` covers case-insensitive and nested password/password confirmation, OTP, identity number/document, API key, secret, token, authorization, cookie/set-cookie, PAN, and CVV fields. Bearer credentials are also removed from otherwise safe log strings. Application code uses the configured redacted channels and does not log request bodies in sensitive flows. Logs should include request_id and trusted tenant_id/actor_id when known. APIs use explicit DTOs/Resources with allowlisted fields and a consistent error envelope containing code, human message, request_id, and safe details.

PAN/CVV never enter ordinary persistence or logs. Provider secrets are never plaintext and cannot be re-revealed. KYC documents use private storage. Future identity numbers are encrypted for retrieval plus keyed-HMAC hashed for per-tenant duplicate checks; OCR is not KYC approval.

Phase 3.1 KYC uses independent authenticated encryption through `KYC_DATA_ENCRYPTION_KEY` for identity/OCR and canonical Tenant+document-type+country+number HMAC matching through `KYC_IDENTITY_HASH_KEY`. Neither persistent-data key may fall back to `APP_KEY`; missing or malformed keys fail closed when KYC cryptography is used. Both keys require a verified data migration before rotation. Model serialization and explicit DTOs exclude ciphertext, HMAC, object keys, signed URLs, raw candidate identity, and OCR payloads. Document images accept only server-sniffed JPEG/PNG/WEBP with valid image dimensions and configured limits; keys are random and never client-controlled.

KYC document access requires `kyc.document.view` separately from `kyc.read`, an active exact-Tenant Admin membership, and current-password confirmation scoped to guard+Admin+Tenant+current password hash within a configured server-side window. Signed application routes recheck signature, permission, Tenant, recent authentication, side, and stored MIME; they are rate-limited and return no-store/nosniff/no-referrer image responses. Audit records only application/side/actor/request, never identity, storage key, or URL. Private objects have no public URL; future S3 pre-signed URLs require HTTPS and very short TTLs.

Audit history is append-only by Application contract and distinct from immutable Ledger history, provider operations, and application logs. Eloquent update/delete guards provide defense in depth but are not claimed to make the database tamper-proof; direct database access remains an operationally privileged boundary. Destructive cascades are avoided for history. Users and tenants transition status rather than being deleted; later erasure/anonymization must never cascade into Ledger history.

Admin models reserve encrypted 2FA secret/recovery fields. Before production, 2FA policy should require PLATFORM_OWNER, TENANT_OWNER, KYC_REVIEWER, and CARD_OPERATOR (and any equivalently sensitive role). Invitations store only SHA-256 token hashes, expire, are single-use, and are scoped to any ACTIVE host that resolves to the invited Tenant. Resending cancels the old token before issuing a replacement. Acceptance locks the invitation, identity, and membership boundary in one database transaction; database uniqueness constraints provide the final duplicate-membership defense. Existing email identities perform independently rate-limited current-password identity confirmation and receive a new membership only—their name and password are not reset and permissions are never copied between Tenants. Raw invitation tokens are excluded from persistence, logs, and rate-limit keys. Invitation mail is sent only after the state transaction commits; a delivery failure cannot roll back an otherwise valid Tenant foundation. Local development captures mail in Mailpit.

Domain ownership verification must not become an SSRF primitive. The local verifier performs no network request. A production verifier should use constrained DNS proof lookup, or an equivalently hardened mechanism with explicit public-address checks, timeouts, response-size limits, redirect prohibition, and no unrestricted HTTP fetches.
