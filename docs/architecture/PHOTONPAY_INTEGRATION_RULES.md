# PhotonPay Integration Rules

2026-09-11 authorized extension: [Card management](CARD_MANAGEMENT.md) supersedes historical Phase 10 exclusions only for the existing PhotonPay regular virtual USD product. It adds scoped management orders, a verified notification inbox, and safe transaction read models; all Ledger, tenant and sensitive-data safety rules remain in force.

The bounded read-only extension now uses `pagingVccTradeOrder` for owned-card
history. See [CARD_TRANSACTION_READS.md](CARD_TRANSACTION_READS.md) for the verified
schema, tenant isolation, pagination, decimal and time handling. The read path never
changes money; approved management flows are governed by CARD_MANAGEMENT.md.

The user-confirmed form revision does not collect an identity number. `ProviderIdentityDocumentDTO.identityNumber` is nullable, and absent numbers are omitted as `certId` from add/edit Cardholder payloads. `certCountryCode` is derived from this cardholder's nationality. No account-identity fallback or OCR is introduced; private document upload and confirmed Provider addition remain mandatory. See `PER_CARD_MATERIALS.md` for legacy request compatibility and the real-merchant contract verification caveat.

Phase 10 supports one PhotonPay product shape: a regular (`recharge`) virtual USD card linked to a READY PhotonPay Cardholder. The configured `cardBin` is an opaque provider product reference and is checked through `getCardBin` before a real issue. The issue request sends the selected Cardholder, the configured USD account, one stable Card Issue Order UUID as `requestId`, and the requested initial card balance as `arrivalAmount`.

The real adapter authenticates with PhotonPay's Basic authorization header and signs the exact JSON request body with the configured RSA PKCS#8 private key using MD5withRSA. GET and file-upload requests do not invent a body signature. Credentials exist only in environment/secret configuration; runtime fails closed if HTTPS, account configuration, or a valid private key is missing. Mock is never a fallback or a staging/production runtime. The user-approved 2026-09-13 exception permits explicit local debug simulation on an isolated database only; see [Local card simulation](LOCAL_CARD_SIMULATION.md). Automated tests retain offline fakes.

## Production runtime selection (2026-09-11)

The user selected PhotonPay production. Runtime defaults and the local deployment select `CARD_PROVIDER_DRIVER=photonpay` and `PHOTONPAY_BASE_URL=https://x-api.photonpay.com`, the production endpoint documented by [PhotonPay](https://api-doc.photonpay.com/?lang=en). App ID, App Secret, RSA private key and USD account ID must be supplied through local environment/secret configuration. Configuration presence is not proof of successful authentication, product eligibility, or completed real card issuing; a live merchant acceptance run is still required. Automated tests use fakes and must never upload materials or spend real funds.

Known `MOCK`, `TEST`, and `DEMO` reference prefixes are rejected before real Provider HTTP calls, and before material submission or financial holds in live Application Actions. The precise `addCardholder` response `data.cardholderId` is persisted; `openCard.cardholderId` must be that saved external ID, never our local application UUID. A successful addition that returns a test ID is unconfirmed, not READY. Existing unused known-Mock holders are excluded from the live active-application selection; their rows are preserved. Null-ID UNKNOWN applications still block new requests, and unresolved issue orders retain their holds and never get automatically retried, settled, or released during this switch. Historical completed cards and accounting are preserved. A used Demo product requires a new genuinely configured product, never rewriting its existing provider reference.

This change concerns the Card provider only. It does not implement other phases' Payment, blockchain, or OCR providers or enable unsupported Card operations.

Account KYC eligibility and PhotonPay Cardholder addition are independent facts. READY now records successful addition with its returned identity, not review approval. Per the approved revision in `PER_CARD_MATERIALS.md`, each requested card collects independent holder details and private uploads; the holder may differ from the account owner. Account identity records and documents are never reused or overwritten. Fresh document bytes are uploaded backend-to-backend through `/file/apiUpload/issuing_cardholder_identity_certificate`, then `addCardholder` is called. Only the resulting application's READY identity may be passed to `openCard`. Encrypted material envelopes/files are private and excluded from ordinary serialization, audit, queue payloads and logs.

Cardholder creation precedes all financial reservation. PENDING, ACTION_REQUIRED, REJECTED, DISABLED, and UNKNOWN cannot issue. An ambiguous `addCardholder` result becomes UNKNOWN and is never blindly retried; status sync is permitted only when a stable Provider Cardholder ID exists. Provider status never changes our KYC status.

Opening a card follows two committed boundaries: TX1 locks and validates Tenant/User/product/Cardholder/Wallet state, creates the order, and posts separate opening-fee and initial-funding holds; the adapter then calls `openCard` without database locks; TX2 applies a trusted result. A timeout keeps both holds and is queried with the same `requestId` via `getRequestResult`. A definitive failure releases both holds. A success creates exactly one safe User Card and settles both holds.

PhotonPay card balance is provider truth and is stored only as a timestamped read-model cache. A safely parsed initial balance, when returned, must equal the requested `arrivalAmount` before settlement; a mismatch stays UNKNOWN. The adapter also validates the returned USD regular-card identity, immediately derives `last4`/masked display, and discards full card number and CVV. Normal issue responses never reveal PAN/CVV. Separately approved management, sensitive reveal and verified notification flows are defined in CARD_MANAGEMENT.md; arbitrary Card balance mutations remain forbidden.
